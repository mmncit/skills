# CLAUDE.md

Guidance for Claude Code and other agents working in this repository.

## What this repo is

A collection of **published agent skills** — one directory per skill, each a coding-guideline document rather than executable code. Pushing to `main` with any `**/SKILL.md` changed triggers `.github/workflows/publish.yml`, which validates every skill's frontmatter and then registers the repo on skills.sh via `npx skills add mmncit/skills`.

This is a **public, user-branded repo.** Treat everything in it as something other people will read with the author's name on it.

## Skill anatomy

```
<skill-name>/
├── SKILL.md          required
├── README.md         optional — GitHub-facing summary
└── references/       optional — deferred detail, loaded on demand
```

**`SKILL.md` frontmatter is exactly two keys, `name` and `description`.** CI parses it with a real YAML parser and fails the build if:

- the frontmatter block is missing or malformed,
- `name` is absent, or
- `name` does not exactly equal the containing folder name, or
- `description` is absent.

Malformed YAML — most often an unquoted `: ` inside `description` — makes the skills CLI *silently skip* the skill at publish time, so it never registers. Wrap the description in double quotes.

**The `description` is the recall surface, not a summary.** It is the only text an agent sees when deciding whether to load the skill, so it must enumerate concrete symptoms and the phrasings a user would actually type — not describe the document. Existing descriptions run 800–1100 characters and read as a list of trigger conditions. Match that.

**Body conventions**, as established by the existing skills:

- Open with the core idea in two or three sentences, then a short diagnostic ("two symptoms that say…").
- Structure the advice as a **ladder of increasing cost**, and state where most readers should stop.
- TypeScript for all examples, `BEFORE`/`AFTER` pairs where a refactor is being shown.
- Close with a **"When NOT to use it"** section that names real costs. This is load-bearing — a skill that only argues for itself gets applied where it doesn't belong.
- Verify runtime claims before asserting them. If a code sample depends on library behaviour (a round trip preserving a field, a flag doing what the docs imply), run it.

## Cross-linking

`functional-architecture` is the designated front door and carries a routing table in both its `SKILL.md` and `README.md`. **When adding a skill, add a row there** and update the "front door of N" heading, or the new skill is undiscoverable from the entry point. Add a reciprocal link in the new skill's "Where to go next".

## Validating locally

CI runs on push; to check first, without writing `node_modules` into this repo:

```bash
npm i --no-save --prefix /tmp/skillcheck js-yaml@4 >/dev/null && node -e "const y=require('/tmp/skillcheck/node_modules/js-yaml'),fs=require('fs'),p=require('path');let bad=0;for(const d of fs.readdirSync('.',{withFileTypes:true})){if(!d.isDirectory()||d.name.startsWith('.')||d.name==='temp')continue;const s=p.join(d.name,'SKILL.md');if(!fs.existsSync(s))continue;const m=fs.readFileSync(s,'utf8').match(/^---\n([\s\S]*?)\n---/);try{if(!m)throw new Error('no frontmatter');const fm=y.load(m[1]);if(fm.name!==d.name)throw new Error(\`name '\${fm.name}' != folder\`);if(!fm.description)throw new Error('no description');console.log('  ok  '+fm.name)}catch(e){console.log('  ERR '+s+': '+e.message);bad=1}}process.exit(bad)"
```

## Not part of the repo

`skills-lock.json`, `.agents/`, and `temp/` are gitignored local artifacts — `skills-lock.json` is generated by `npx skills add` and is not the registration mechanism. Don't commit them, and don't "fix" them when they look stale. If you install anything for a local check, keep it out of the working tree.
